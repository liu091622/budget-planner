1. 背景与用户问题
 
1.1 用户问题清单
 
本产品的需求来自用户本人对日常资金管理痛点的描述，共归纳为四类核心问题：
• P1 预算有限，不知道怎么花钱：收入固定且有限，面对多项开支没有整体规划，钱花到哪里没有概念，月底容易吃紧。
• P2 生活费缺乏分配方案：生活费（或工资）到手后，没有按项目分配（如餐饮、交通、娱乐、储蓄），日常消费凭感觉。
• P3 买东西纠结性价比：购物前在“买/不买/买哪个”之间反复纠结，缺少量化的比较依据和预算约束参考。
• P4 出去玩不会做预算计划：出行（如短途旅游、聚餐、活动）时，不知道要准备多少钱、各项怎么分配，容易超支或拉兴。 
1.2 证据状态
 
以上问题目前为用户场景描述（一手需求），尚未经过系统化验证。上线前需通过访谈与问卷验证问题优先级与目标用户范围（见“目标用户”与“开放问题”）。
 
2. 产品目标与成功指标
 
2.1 产品目标
1. 用户在录入收入与开销后，获得一份可执行的分配方案，明确“这个月每类能花多少”。
2. 在消费过程中，系统及时提醒容易乱花钱的地方（分类超支、高频小额、冲动消费），并给出省钱思路。
3. 系统只提供方案、提醒与建议，不做强制限制，最终选择权始终在用户手中。 
2.2 成功指标
• 分配方案创建率：录入收入后创建/确认分配方案的用户占比（月）[目标值待产品确认]
• 方案采纳率：当月消费在方案各分类额度内的用户占比[目标值待产品确认]
• 超支月份占比：当月支出超过收入的月份占比（按用户月）较使用前下降[待基线数据确认]
• 预警查看与反馈率：用户查看预警详情、标记“有用”的比例[目标值待产品确认] 
3. 范围与非目标
 
3.1 范围（MVP）
• F1 收支录入：快速记录收入与开销，支持分类、金额、备注。
• F2 分配方案生成：基于收入与固定支出自动生成分配方案，支持用户调整。
• F3 乱花钱提醒：分类超支、高频小额、单笔异常消费三类预警。
• F4 省钱思路：基于当月消费结构生成个性化、可溯源的建议。
• F5 购物性价比参考：为“买不买”的纠结场景提供量化参考。
• F6 旅行与活动预算：为出行/活动创建独立预算并跟踪支出。 
3.2 非目标
• 不绑定银行卡、不自动扣款、不做支付功能。
• 不强制限额、不拦截消费——一切约束仅以提醒形式呈现。
• 不做理财、投资或信贷产品推荐。
• 不做社交、社区、分享功能。
• 不做复式记账、多币种、发票管理等复杂账本能力。 
4. 核心原则
• 原则一：建议不强制。系统输出分配方案、预警与省钱思路，均为"参考信息"，用户可采纳、调整或忽略，任何环节不剥夺用户决策权。
• 原则二：输入要快。一次记账最多3次点击完成，不做繁琐分类表单，降低坚持记账的门槛。
• 原则三：数据私有。消费数据默认仅用户本人可见，不做公开展示，不向第三方共享。 
5. 目标用户与使用场景
 
5.1 目标用户画像（假设，待MVP前访谈验证）
• 人群：在校学生（大学生为主）、刚工作的年轻人，约18-30岁
• 收入特征：收入固定且有限（生活费/工资/兼职），月收入与月支出接近，结余少
• 行为特征：消费冲动多（外卖、网购、娱乐），对记账工具坚持度低，需要“少操作、快反馈”
• 决策特征：希望有人（或系统）给参考意见，但讨厌被强制管束 
5.2 关键使用场景
• S1 月初分配：生活费/工资到账，录入收入后，系统给出“餐饮、交通、购物、娱乐、储蓄”等各类可用额度，并显示日均可花金额
• S2 日常记账：每次消费后（外卖、打车、网购），几秒记一笔账，看到本月还剩多少、哪类快超了
• S3 购物纠结：看中一件商品，价格不便宜，纠结买不买。输入商品价格，系统结合剩余预算给出“买/缓买/不买”的量化参考与理由
• S4 出行计划：计划出去玩（短途旅游、聚餐、活动），按交通/住宿/餐饮/门票等项做预算，活动期间单独记录，实时看剩余
• S5 月底吃紧：月中发现钱快花完了，系统指出钱花在哪里、给出接下来两周的省钱思路 
6. 产品核心流程
 
产品形成"录入 -> 分配 -> 消费 -> 预警 -> 建议 -> 用户决策"的闭环，用户决策（采纳或忽略）后回到日常记账，持续迭代方案与建议。
 
7. 功能需求与验收标准
 
以下需求统一采用"行为 + 可观察结果 + 失败边界"写法，验收标准均为可测试项。
 
7.1 F1 收支录入
 
行为需求：用户在"记账页"选择收支类型（收入/支出）与分类，输入金额，可选填备注，点击保存后该笔记录进入当月流水，当月收入、支出、剩余金额即时更新。
• 收入分类：生活费/工资/兼职/奖学金/其他。
• 支出分类（默认）：餐饮/交通/购物/娱乐/学习/居住/医疗/其他。
• 高频分类（如餐饮、交通）支持一键复用上次分类与金额输入习惯，减少点击。 
验收标准：
• A1.1 保存：录入支出后，首页当月“支出”与“剩余”数字立即更新，流水列表出现该记录
• A1.2 编辑删除：修改或删除一笔记录后，当月汇总与关联预警状态同步重算，无残留旧值
• A1.3 非法输入：金额为空、为负、非数字或分类缺失时，保存被拦截并给出明确提示，不产生脏数据 
7.2 F2 分配方案生成
 
行为需求：用户在录入收入后，系统按默认规则生成分配方案；方案以分类额度列表呈现，并展示每类"剩余可用"与"日均可用"；用户可调整各分类比例或金额，调整后方案即时重算。
• 默认分配规则（可配置）：先扣除固定支出（如房租、话费），剩余部分按参考比例分配——必要开支（餐饮/交通/学习）约50%、想要开支（购物/娱乐）约30%、储蓄约20%。该比例仅为默认建议，用户可完全自定义。 
验收标准：
• A2.1 生成：录入收入后一键生成方案，每类显示额度、剩余可用与日均可用（剩余/本月剩余天数）
• A2.2 调整：调整任一分类额度后，其他分类额度自动重新计算，总额不超收入，无冲突状态
• A2.3 无收入：未录入收入时，方案页提示“请先录入收入”，不生成空方案 
7.3 F3 乱花钱提醒
 
行为需求：系统在记账提交后即时检测三类预警，并在首页"预警卡片"汇总展示；提醒文案采用中性表述，不做道德评判。
• 预警类型 1：分类超支。触发条件：某分类当月消费达到方案额度的80%（提示）、100%（警示）。示例：“本月餐饮已用额度的80%，剩余额度约×元”
• 预警类型 2：高频小额。触发条件：同一分类7天内消费次数≥阈值（默认7次）。示例：“本周外卖已点8次，累计花费×元”
• 预警类型 3：单笔异常。触发条件：有历史数据后，单笔金额显著高于该分类近30天均值（默认≥2倍）。示例：“这笔×元高于你近一个月购物类平均消费，请确认” 
验收标准：
• A3.1 触发：记账提交后，命中阈值的预警在1秒内出现于首页预警卡片
• A3.2 忽略：用户可关闭单条预警；关闭后24小时内同类条件不再重复打扰
• A3.3 中性表述：全部预警文案只陈述事实与数字，不含“你乱花钱”“太浪费”等评判性措辞
• A3.4 无数据降级：无历史数据时，“单笔异常”预警不启用，不产生错误判断 
7.4 F4 省钱思路
 
行为需求：系统基于当月消费结构生成3-5条省钱建议，每条建议必须关联具体分类与数据，可溯源；用户可对建议标记"有用／没用”，反馈进入优化。
 
验收标准：
• A4.1 个性化：建议与用户当月消费数据相关，例如“本月外卖占餐饮60%，试每周2次自己做饭”；不得输出与数据无关的通用鸡汤
• A4.2 可溯源：每条建议展示依据（关联分类、占比或金额），点开可见对应消费明细
• A4.3 估算标注：涉及“预计可省X元”时标注为估算，并说明计算口径（基于近30天均值）
• A4.4 无数据降级：当月数据不足时，仅输出基于默认规则的建议并标注“通用建议” 
7.5 F5 购物性价比参考
 
行为需求：用户在"纠结买不买"场景输入商品名称与价格（可选输入同类备选项进行对比），系统返回参考结论与量化理由：预算是否充足（对比剩余可用额度与日均可用）、与同类历史消费的比较、建议（可买/缓买/不建议），并明确提示"仅供参考，最终由你决定"。
 
验收标准：
• A5.1 量化依据：参考结论必须附带至少一项量化依据（剩余额度对比/日均额度对比/历史同类均值）
• A5.2 决策权声明：结果页固定展示“最终决定权在你”，不出现强制“禁止购买”类操作
• A5.3 对比输入：支持输入多个备选商品，以表格并排比较价格与参数摘要 
7.6 F6 旅行与活动预算
 
行为需求：用户创建活动（如"周末南京两日游"），设置活动名称、日期与预算总额（可自动按项目分配：交通/住宿/餐饮/门票/其他）；活动期间产生的支出可在记账时归属该活动，活动页实时显示已用与剩余；活动结束后可归档。
 
验收标准：
• A6.1 创建：创建活动后生成预算页，显示各项目额度与总额
• A6.2 归属：记账时可选择归属活动；归属后活动剩余金额实时扣减，且不影响日常分类统计口径（或单独列示）
• A6.3 归档：活动结束后归档，归档后不可再新增归属记录，历史可查 
8. 异常与边界
• 收入为0或未录入：不生成分配方案，方案页提示先录入收入
• 当月支出超过收入：允许记账，状态标记“本月已超支”，展示超支金额；不拦截、不施压
• 极端金额：金额上限（如单笔≤999,999元）与精度校验，超出给提示；负数拦截
• 无历史数据：涉及均值/历史的预警与建议自动降级为默认规则，并标注“通用”
• 跨月切换：支持查看历史月份，本月数据为当前操作对象；上月未用完额度默认不结转（规则可配置） 
9. 非功能需求
• 隐私与安全：消费数据仅本人可见；不做公开榜单；账号体系内数据隔离；删除账号可清除全部数据（具体策略[待产品确认]）
• 易用性：单次记账≤3次点击；核心操作（记账/看方案/看剩余）首屏可达
• 性能：方案生成、预警计算在1秒内返回[目标值待确认]；月流水1万条以内操作不卡顿
• 兼容性：适配目标平台（端形态待确认：小程序/App/Web）主流机型与系统版本 
10. 信息架构与页面结构
• 首页看板：本月收入/支出/剩余、方案进度条、预警卡片、今日可用额度 (关联: F2/F3)
• 记账页：收支类型、分类、金额、备注、活动归属（可选） (关联: F1/F6)
• 方案页：分类额度列表、调整控件、重置、日均可用 (关联: F2)
• 建议页：省钱思路列表（可反馈）、购物参考入口与结果 (关联: F4/F5)
• 活动页：活动列表、单项预算明细、已用/剩余、归档 (关联: F6)
• 流水页：按月流水明细、分类汇总、编辑/删除 (关联: F1) 
11. 依赖与开放问题
11.1 依赖
• 账号与数据存储服务（用户数据隔离、跨端同步能力）。
• 端形态（小程序/App/Web）确认后，方可确定开发栈与排期。
• 预警阈值、分类体系的默认配置需要产品确认后固化。 
11.2 开放问题
• 分类体系：内置默认分类是否足够，用户自定义分类在V1还是V2支持
• 预警阈值：80%/100%、7次、2倍等默认值是否开放给用户自定义
• 目标用户验证：MVP 前是否做访谈/问卷验证用户画像与问题优先级
• 数据来源：V1 为纯手动记账；是否规划接入账单/支付平台自动同步（依赖外部授权）
• 成功指标基线：“超支月份占比下降”需要使用前基线数据，采集方案待定 
12. 版本规划
• V1 (MVP)：F1 收支录入、F2 分配方案、F3 乱花钱提醒、F4 省钱思路
• V1.1：F5 购物性价比参考、预警阈值用户自定义
• V2：F6 旅行与活动预算、自定义分类、多设备同步、历史数据报表 
说明：以上版本排期与优先级待产品评审确认；所有[待确认]项需在进入开发前由产品负责人给出结论。
